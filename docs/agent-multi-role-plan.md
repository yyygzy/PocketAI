# 本地 Agent 改造方案与验证方案：中心管控 + 多角色协作 + 显存错峰

状态：待评审（未开工）。依据 = 2026-10-15 源码回读 + 本机三探针实测（GTX 1050 Ti 4096MiB / Ollama 0.33.1）。
关联：`docs/v4-iteration-ledger.md`（实施后逐条回填）、`docs/verify-checklist.md`（验收行从 **B72** 起，不重排）。

---

## 0. 目标与不做什么

**目标**：让 agent 的编排形状由**本机环境**决定，而不是由"我们假设用户有一张好卡"决定；并把已经存在却没接线的两处调度接缝用上。

**不做**（明确排除，避免范围漂移）：
- 不做多机/分布式执行；不做常驻 worker 池；不引入新的持久化文件格式（判据结果沿用 `app_config` 单键 JSON，形状同 `src/main/agent/text-protocol-prefs.ts:13`）。
- 不做嵌套树状 UI。理由与既有口径同源（`docs/v4-iteration-ledger.md` 里"记录跳回轮次→不做：缺的只是关联键，而用户不会用它跳回"）：角色归因只做**扁平带标签**，出现在现成的分步明细里（`src/renderer/src/modules/agent/chat/AgentPanel.tsx:517`）。
- 不改工具授权口径：`'*'` 只给内置这条单一来源（`src/main/tools/registry.ts:68-84`，三处判定点 `:75-77` 自述）保持不动，子代理只能继承、不能扩权。
- 不在本轮把"助手默认模型"从渲染层迁到主进程。它**当前是生效的**（`src/renderer/src/modules/chat/ChatModule.tsx:227/420/443` 会把 `asst.defaultProviderId/defaultModel` 写进 `targets`），只是引擎不读库字段（`src/main/agent/engine.ts:683` 取 `targets[0]`）。⚠️ 更正一条调研误报：曾有结论写"没人读、默认模型不生效"——被 `ChatModule` 那三处证伪。

## 2. 判据层设计（L0）：三条正交的判据，不要混成一个"档位"

1. **容量判据**（能不能同时驻留、能不能并行）
   - 输入：总显存（已有）+ used（新增）+ 各模型权重体积（M1，新增保留）+ KV 预算（V-0 已测：约 40–45MiB / 1k token，见 M9——**不是**主要开销）。
   - 输出：`maxConcurrentChatSlots`、`allowChatEmbedOverlap`、`rolesMayUseDistinctModels`。
2. **能力判据**（这个 `providerId::model` 派得出委派吗）
   - 输入：一次探针请求的结果，三态 `native_tools_ok | fence_only | no_delegation`，外加模型标识（`/api/tags` 的 digest，模型换了要重探）。
   - 存储：`app_config` 单键 JSON 数组，键形状复用 `textProtocolKey` 的 `providerId::model`（`text-protocol-prefs.ts:22`）。上限与清洗规则照抄那份（防脏值撑大 KV）。
3. **成本判据**（这轮编排值不值）
   - 输入：现成 `recordPerf` 的 `agent.total`（标签由 `perf-probe.ts:68-76` 按 `kind` 拼出，慢阈值 `:36/:38`）+ 每次委派热态 1.34s（M7）。
   - 输出：预算闸门（总 LLM 调用数 / 总墙钟），**不是**给用户看的档位。
   - 已知缺口：`kb.*` 标签不带 `provider/model`（`rag.ts:438` 等），跨模型归因时看不出来 ⇒ 判据层顺带补标签。

三条正交的意义：`入门档 + 有能力` 可以开顺序委派（同模型换帽子）；`旗舰档 + 无能力` 一律不开管控者。**混成一条档位就会两头误判**。

V-0 跑完后补一条口径修正（写在这里以免有人再按初稿理解）：低配机的容量闸**不是**"只能一个模型"，
而是 **M10——chat 模型与 embedding 模型不同驻**（2.7GB 权重 < 4GB 仍被逐）。两个 chat 模型在
`num_ctx≤2048` 下反而能同驻（M3）。所以"入门档强制同模型"这条默认**仍然成立，但理由换了**：
不是因为放不下两个角色模型，而是因为**任何一个角色一旦走检索链，就会把对话模型挤出去**（M10 实测
下一步要付 3045ms）。这条理由是 141 槽位划分的主轴，不是 147 的档位表。

## 3. 改造项（实施顺序即依赖顺序；每项一个台账编号，做完停下等提交）

### 已取消的前置小项：围栏抽取路径补 `name` 白名单（写下过，随后被自己证伪，留此防止重犯）
- 原判断：`text-tool-protocol.ts:68-74` 的围栏路径不校验 `name ∈ knownToolNames`（白名单只出现在 `:91` 的无围栏兜底），而 `engine.ts:1220` 已把 `known` 传进来 —— 看起来是个执行面缺口。
- **证伪点（回读源码，不是推理）**：`tools/registry.ts:164` 对找不到 schema 的名字直接 `{decision:'deny', reason:'UNKNOWN_TOOL'}`，紧随其后的授权检查给 `TOOL_NOT_ALLOWED`。⇒ 抽取阶段放行的未知名字**根本走不到执行**，它变成一条错误工具结果回给模型，模型还有机会有改名重试。
- 反而有害：若在抽取阶段静默丢弃，`calls=[]` 而 `fenced.length>0` 会让 `:74` 提前 return（宽松兜底也不再生效）⇒ 整段回复被当成**最终回答**呈现。用户看到的是"答非所问"而不是"某个工具不允许"——**把一个可诊断的拒绝换成一个不可见的降级**。
- 结论：不做，产品代码不动。这条更正同时**收紧了决策①**：真正的守卫是围栏标签本身，不是名字白名单——白名单挡不住"知名工具 + 合法参数"（那本来就该放行），所以将来若真放宽标签，补白名单并不能把风险降回原状。
- 顺带记一条测试现状：`tests/text-tool-protocol.test.ts` 的围栏用例**全都不传** `known`（用的名字是 `a`/`b`/`calc`），所以这条不对称从未被断言过，也说明它不是刻意设计。若要留东西，只留一条**记录型用例**钉住"未知名字交给 registry 拒、抽取阶段不吞"，那不是行为变更。

### V4-Iter-140 判据底座（只读，不改行为）
- 落点：`ollama-runtime.ts:128` 保留 `size/digest`；`hardware.ts` GPU 项加 `usedMiB`（NVIDIA 走 `nvidia-smi`；非 NVIDIA 用 `/api/ps` 的 `size_vram` 汇总兜底，Mac 明确置 `null` 并在 UI 说"未测得"）；新增纯函数模块 `src/main/agent/local-capacity.ts`。
- **判据形状改为"实测表 + 保守默认"，不给公式**（V-0 定的）：M3 显示 2048 与 4096 之间只差 128MiB 就翻边、M10 显示 2.7GB < 4GB 仍被逐 ⇒ 任何 `totalMiB - Σweights - kv > 0 即同驻` 的算术都会给出错答案。表内每条阈值都必须带"在哪台卡、哪个 ctx 测得"，采不到就退到"chat 与 embed 不同槽 + 同时只放一个模型"的默认。
- **顺带一条能白拿的杠杆**：`num_ctx` 从未被应用设置（全仓零命中），本地跑都吃 Ollama 默认 4096。M9 实测 2048→8192 只多 ~220MiB，但 4096→2048 恰好把"两个 chat 模型同驻"从不可能翻成可能 ⇒ 140 应把"是否给本地 provider 显式设 `num_ctx`"作为一个判据输出项列出来（默认不动行为，只报"当前未设"）。
- 为什么单独成迭代：这一层是全系列唯一能"零风险先落"的部分，且**纯函数住在中立模块**（不寄居在常被整体 `vi.mock` 的 `rag.ts`/`engine.ts`，同既有教训）。
- 边界：不改任何调用点；`usedMiB` 采不到就是 `null`，判据退回保守档。
- 验收：B72（CI：判据表逐档对号 + 两条反向对照——"权重相加放得下"不得判成可同驻（M10 的形状）、`/api/ps` 的条数不得当成显存真相（A1 §7 三同挂 vs A2 生成态驱逐就是这个坑））。

### V4-Iter-141 本地槽位调度（错峰主体）
- 落点：把 `src/main/chat/concurrency.ts` 的 `withProviderLimit`（现容量 2、唯一使用者 `chat-service.ts:526`）扩成 `withLocalSlot(kind, providerId, model)`：`kind ∈ {foreground, retrieval, background}`；按 140 的判据给容量。
- **接线清单（回读后补全，漏一处就等于 139 那种"没接线"缺陷重演）**：
  - agent 侧 4 处 `streamChat`：`engine.ts:392`（历史压缩）、`:856`（规划）、`:1083`（主循环）、`:1670`（步数耗尽兜底）。原调研只点了 `:1083`。
  - 检索链 4 处：`knowledge/reranker.ts:71`、`knowledge/hyde.ts:22`、`knowledge/multi-query.ts:53`、`knowledge/ocr.ts:41`。
  - 标题：`conversation/title-gen.ts:65`。
  - embedding **不是** `streamChat`：`knowledge/embedding.ts:31`（批量，走 `adapter.embed` → `/v1/embeddings`）与 `:56`（查询）。⇒ 它和 chat 是两条端点；M10 更直接：**在 4GB 机上 embed 一到就把对话模型顶出去**（2.7GB < 4GB 仍被逐），所以"槽位按端点分"不是洁癖而是硬约束。卸载也一样不对称——M4 记的是两次实测结论相反（`/api/generate keep_alive:0` 有时卸得掉 embedding 模型、有时卸不掉），**唯一稳定的是按加载它的那条端点去卸**（`/api/embed keep_alive:0` 两次都清空）。
- 让路：`knowledge/index-queue.ts:39 isIdle()` 现在零调用者 ⇒ 后台任务出队前先问前台槽是否空闲；**只在空闲期跑**，不做 kill 式抢占（前台 run 内部会调 `kb_search`，误判"空闲"会自锁）。
- 让位卸载：默认**不**主动 `keep_alive:0`（冷启动代价实测：M7 5.2s、M10 3045ms）；仅在"后台大批量索引 + 前台长时间无请求"时由用户显式开，且**必须按端点成对卸载**（chat 走 generate、embed 走 embed），否则留下卸不掉的驻留反而更挤。
- 边界与回滚：判据拿不到 ⇒ 沿用今天的容量 2，行为不变。云 provider 不受本地槽位约束（只有 `type==='ollama'`/回环 baseUrl 这条判据参与的才走）。
- 验收：B73（CI：假时钟下排队顺序与并发数；M5 的 +64% 互拖用一条"检索链与索引不得同槽"断言守住）、B74（🔶 真机：4GB 机上聊天期间灌索引，看 `agent.total` 变化——数字只有真机可看）。

### V4-Iter-142 能力探针与三态徽标
- 落点：`src/main/agent/delegate-capability.ts`（纯函数判卷）+ 一次真实请求（走 `providerManager.getAdapter().streamChat`，带 `tools`，同 M7 形状）；结果写 `app_config`；设置页 → 模型服务商处显示 `可委派 / 只会写围栏 / 不派活`。
- 硬规矩：探针**不许**在文本协议模式下跑（M8 证过那条路会假阴性）；探针失败按 `hasIpcFailed` 那套"失败是返回值"的合同处理（V4-Iter-139 教训），不许把失败当"不支持"。
- 判卷口径：至少 3 次重复，全过才记 `native_tools_ok`（M7 里 3b 是 4/4，但单次不足以定论；稳定性本身列为待测 V-1）。
- 验收：B75（CI：判卷纯函数三态 + 反向对照"文本协议结果不得判成 ok"）、B76（真机：本机三个模型应分别落 `ok / fence_only / no_delegation`，这是探针自证）。

### V4-Iter-144 `delegate_task` 内置工具 + 子 run（顺序形态）
- 落点：新增内置工具（注册进 `src/main/tools/registry.ts`）；执行分支在 `engine.ts:1441-1525` 处 fork：**直调 `agentEngine.run`，绕开 `chat-service.ts:174` 的会话锁**（同会话走 `send` 必自锁死：`withConversationLock` 把 agent 分支整个包住）。

## 4. 验证方案（三层，逐条标注"谁能证"）

**V-0 先补的实测 —— 2026-10-15 已跑完（本机 4GB），结果见 M3/M9/M10，并推翻初稿一条结论**
- 做了什么：同一模型 `num_ctx` 512/2048/8192 的 `/api/ps.size_vram` + `nvidia-smi used` 双读；双 chat 模型在 ctx 512/2048/默认 4096 下的同驻性；chat 与 embed 混跑后的驱逐；卸载对称性。
- **推翻的初稿结论**：M3 原写"两个 chat 模型不能同驻"。实测 ctx≤2048 时**能**同驻（3149MiB），不能的是"默认 4096"那一档 ⇒ 我把"驱逐"当成了容量本质，其实它是 ctx 与 Ollama 预算的合成效应。
- **新发现的硬约束**：M10 —— chat 模型与 embedding 模型在 4GB 机上不同驻（2.7GB < 4GB 仍被逐，被顶出后一步付 3045ms）。低配档的真实理由换成这条。
- **未收敛，不许当结论用**：M4 —— `/api/generate keep_alive:0` 对 embedding 模型两次实测一卸一留 ⇒ 只准用"按加载端点对称卸载"。
- 现场纪律（已按此执行四轮）：gitignored `data/*.mjs`；跑完 `/api/ps` 空 + `nvidia-smi used=0MiB` + 关 serve + 删脚本 + `git status` 干净。

**V-1 CI 层（能进 CI 的一半，必须全部进）**
- 判据纯函数真值表；槽位排队（可控假时钟，断并发数与顺序）；能力判卷三态 + 反向对照；`delegate_task` 入参 schema（**新建/默认载荷必须能过 schema**，同 V4-Iter-94 那条教训）；子作用域收窄（工具/库子集）；会话锁不死锁；trace 归因列往返；桥层（复用 139 那层：真 preload ⇄ 真 handler ⇄ 真临时库）。
- 变异实测要求（每个新闸门至少一轮，且必须**转红**）：删掉 `withLocalSlot` 一处接线 / 把子级白名单改成父级全量 / 让 confirm 工具重新进子清单 / 判据 false 时仍发第二模型请求 / 归因列不写 / 能力探针改走文本协议。恢复一律 `assert count==1` + sha256 核对 + 逐处 `git diff` 复查。

**V-2 真机/探针层（CI 证不到的，写清"只有肉眼或只有真机能看"）**

## 5. 风险与停止条件

| 风险 | 处置 |
|---|---|
| 编排把成本乘上去：父 15 步 + 每子 15 步，本地 1.3s/次 ⇒ 一个"看起来更聪明"的任务实际几分钟 | 144 的预算闸 + 146 的耗时预估先行显示；预估只准引用实测数字 |
| 低配机上"多角色"退化成同模型换帽子，用户体感与单 agent 无差别 | 理由按 V-0 换成 M10（跨模型角色一遇检索就互相顶出显存），不是"放不下"。文案不许暗示"多模型协作"；判据屏写清"本轮所有角色共用同一模型" |
| 子代理撞确认闸造成的静默失败被当成结果 | 144 规定派发前过滤；桥层用例反向钉"confirm 不得进子清单" |
| 同一授权口径散落多处（`registry.ts:75-77` 三判定点） | 子作用域只做**收窄**，任何"扩权"路径必须在 CI 里被一条反向对照挡下 |
| `app_config` 存判据结果 = 新事实来源，模型换了就过期 | 存 digest；digest 变化即视为未探；探针失败不当结论 |

**停止条件（V-0 已跑，逐条落到"触发/未触发"）**：
- 原设的触发条件——"4GB 机上 `num_ctx 2048` 放不进两个 chat 模型"——**未触发**：实测能同驻（3149MiB）。所以 145/147 的跨模型角色不必整块挪出低配档。
- 但 V-0 换了一条更硬的理由让低配档**仍然默认关跨模型角色**：M10——任一角色走检索链（embedding）就会把对话模型顶出显存，代价 3045ms/次。**跨模型角色在低配档不是"放不下"，而是"一检索就全盘慢下来"**，默认关闭的理由从容量改成了混跑驱逐。
- 新的触发条件（等第二台机器）：≥6GB / ≥12GB 档的"chat 与 embed 可否同驻"没测 ⇒ 147 的这两档在拿到数据前只准标"依据不足，按低配默认"。

## 6. 待你点头的三个决策（不决定就没法把 140 之后的口径写死）

1. **围栏标签要不要放宽 —— 已定论：本轮不放宽**（2026-10-15 跑了 50 例正向 + 24 例反向对照，本机 coder-1.5b / 1.5b-instruct / 3b-instruct，提示词逐字取 `buildTextProtocolPrompt`）：
   - **收益实测**：`coder-1.5b` 文本协议下现正则可抽 **5/20 = 25%**，放宽后 **10/20 = 50%**（围栏标签分布 `json×7 / tool_call×4`）；`1.5b-instruct` 10%→20%（`json×4 / swift×1 / tool_call×2`）；`3b-instruct` 0/10→1/10。
   - **为什么仍不值得开**：50% 远够不到"管控者"（对照 M7：3b 走**原生 tools** 是 4/4）。⇒ 放宽的真实用途只是"子角色在小模型上偶尔吐出可执行调用"，**不是**低配机多角色的入口。`swift×1` 这种标签也说明放宽会把普通代码块纳入解析面。
   - **反向对照**：普通"给我一段 JSON"的请求里，coder 12/12 都出围栏、3b 8/12 出围栏，但被误判成工具调用的 **0/24**（含一条我故意写的"字段有 name 和 arguments 的示例"）。样本小，只说"未观测到"，不说"安全"。
   - **顺手挖出的一条"看着像缺口"，回读源码后判定为不存在**（详见 §3 开头那条"已取消的前置小项"）：围栏路径不校验 `name ∈ knownToolNames` 看似允许任意执行，实际 `registry.ts:164` 早已 `UNKNOWN_TOOL` 拒绝；而在抽取阶段补白名单会把"可诊断的拒绝"换成"静默的最终回答"。⇒ **不改产品代码**，且由此得出更硬的一条结论：**守卫是标签本身**，白名单拦不住"知名工具 + 合法参数"，所以放宽标签的代价无法用白名单补偿。
   - **第三种形状（记档，未处理）**：真实样例里出现过 `tool_call {\n "name": "kb_search", "arguments": {...} }`——没有 ``` 围栏、只有前导词 + 裸 JSON。两条正则都抓不到，而现有兜底要求整段 `startsWith('{')`（`:78`）也抓不到。若将来要救这类模型，必须新增这第三形状，并配自己的反向对照。
2. **子代理要不要独立会话**：绕锁直调 `agentEngine.run` 最省，但会话归属与 trace 呈现要定规矩（现有口径：Agent 只记助手 + 会话，不做记录跳转）。
3. **低配机默认开不开"顺序委派"**：M7 显示本机只有 3b 能当管控者（1.5b 一档 0/4）⇒ 是"探测到有能力才开"，还是"入门档一律不开、由用户在判据屏手动开"。
