## 一、审计范围与方法

1. **模块深读**（人工逐行）：`src/main/knowledge`（17 文件，检索链路）、`src/main/agent`（engine 1632 行 + 审批 + safe-params）、`src/main/tools`（13 文件，含 shell/fs/sandbox 边界）、`src/shared/text-tool-protocol.ts`、`src/shared/tool-preview.ts`。
2. **并行子审计 4 路**：加密与密钥（crypto/lock/license/backup/secret-store）、IPC 与网络边界（ipc/preload/net/files/export/channels）、代码执行与外部集成（mcp/sandbox/terminal/python/skills/assistant 导入导出）、渲染层与 Electron 配置（窗口 webPreferences/CSP/markdown/mermaid/导出）。
3. **证据复核**：子审计全部 Critical/High 逐条回读源码定位行号，剔除 1 条被实测证伪的结论与 2 处路径/事实错误（见第三节）。
4. **实测验证**：在工作区 `data/csp-probe/`（gitignore 内）用 Electron 44 起 `show:false` + `sandbox:true` 窗口 `loadFile` 一个含内联脚本的页面，同时注册 `onHeadersReceived` 注入 `script-src 'self'`，采集 `console-message`。结论见第三节第 1 条。探针目录已删除，未改动任何生产代码。

## 三、结论纠正（子审计复核 + 自身修复计划的假设证伪）

1. **「生产环境 CSP 实际零生效（`file://` 不适用 `onHeadersReceived`）」— 误报。** 实测：`onHeadersReceived` 对 `file:///…/page.html` **有回调**，注入的 `script-src 'self'` **确实拦住内联脚本**（渲染端输出 `Executing inline script violates the following Content Security Policy`，内联脚本未执行）。故 `csp.ts` 的纵深防御在主窗口/浮窗/detached/unlock（均 `loadFile`）上生效，不必修 `<meta>`（可作双保险，但不是洞）。SEC-17 据此收窄到 `data:` 文档这一条路径。标记：`误报`。
2. 路径纠正：secret-store 实际在 `src/main/crypto/secret-store.ts`，不在 `src/main/db/repositories/`。
3. 事实纠正：不存在「`Math.random` 用于密钥」（仅临时文件名，见 SEC-15）；scrypt 参数为 N=32768/r=8/p=1（约 32MiB，代码注释写 64MB 有误）。

SEC-Batch-2 动手前对**本台账自己写的修复计划**做了一轮证伪，三条被推翻/改写：

4. **SEC-4「未授权的工具被执行」— 部分证伪。** `classify`/`execute` 按 name 找到 schema 后还有 `allowedToolIds.has(schema.id)` 二次校验（`registry.ts:143,188`），所以「只勾 MCP 那条 id」的结果是 `deny TOOL_NOT_ALLOWED` 而非越权执行。真实缺陷改述为：`*` 授权下的**行为静默替换**、跨 Server 同名的**恒路由到第一个**、`tools` 数组**同名重复项**。结论（改名 + `remoteName`）不变，理由换了。
5. **Step D「导入即落地执行」— 部分证伪。** 全仓无 MCP 开机自启（`index.ts` 不调 `mcpManager`），import 只写库；Agent 侧 `listMcp()` 只收 `status==='running'` 的运行时（`registry.ts:27-31`）。故执行闸门是「点启动」，修复不需要导入期拦截。
6. **Step E「导入清空 `toolPermissions` 即收回权限」— 证伪。** `engine.ts` 原有无条件 `[] → ['*']` 让清空等于保持全授权（且 9 个内置助手里 7 个本来就是 `[]`）。已按选定口径改为：空数组=无工具，仅「未选助手」与「内置助手」保留旧语义；该规则抽成纯函数 `resolveAgentToolPermissions` 并补单测。
7. 附带修正一处自我规格：MCP 启动命令预览最初实现为「trim 每个参数」，实测会让 `python -c "rm -rf /"` 展平成看不出参数边界的 `-c rm -rf /`——安全确认场景里保真优先，改为含空白参数加引号呈现。
8. **SEC-6 的「恢复无确认」表述不准**（Batch-3 复核）：渲染层正常路径本就弹 `bk.localRestoreConfirm` 危险确认，缺陷实质是**确认只存在于渲染层**、主进程对路径来源无权威。修复方向不变（把权威移进主进程的令牌机制），但严重度描述按此改写。另：`z.tuple([obj.optional()])` 对「无参数调用」实测可过（`[]` 与 `[undefined]` 均 success），因此给可选入参的 handler 加 schema 不会打断首次调用。
9. **SEC-9 的「等于无审批 RCE」表述过重**（Batch-4 复核）：`shell-config.ts:3-4` 写明 `agent.shell_policy` 缺省即 `confirm`（逐条确认），`auto-safe` 是用户在 Agent 工具栏显式选择的降级。故准确说法是「降级选项中存在绕过洞」。另实测确认两条正则事实：`deno eval` 是子命令形式（无短横线，需单独规则）、`MCP_TOOL_NAME_RE` 允许数字开头/连字符（故 SEC-4 的清洗分支必要）。
10. 一处实现被自己的单测推翻：`assertWithinWorkspaceByRealpath` 接入 `files-service` 后，6 个用假 `DATA_DIR`（不存在的 `C:\pocketai-test-data`）的既有用例全红——根因是守卫在**工作目录本身不存在**时抛「路径校验失败」。这不是测试该改，而是守卫该放行：目录不存在时路径上没有任何既存节点可构造链接逃逸，让后续 fs 以 ENOENT 自然失败更可诊断。已按此修守卫并补一条专门用例。
11. **Batch-5 动手前实测自己 SEC-18 的两条前提，双双推翻**（对本机 better-sqlite3 + `tokenize='trigram'` 直接建表验证）：① 「两路 score 语义混用会污染 MMR」不成立——`rrfFuse` 用 RRF 名次分数覆盖向量/BM25 各路原始分数，进 MMR 的分数永远同源；② 「改中文检索需要一次全库重索引」不成立——trigram 索引侧不动，只改查询串（CJK 切 3 字滑窗 OR）即可，实测旧写法 0 命中、新写法命中且多窗口片段排名更前。
12. 实测踩到反向陷阱：trigram 表上 `LIKE '%库%'`（1 字符）被索引加速后**静默返回空行**（≥2 字符正常），比抛错更危险 ⇒ 短 CJK 查询不做 LIKE 兜底，交给向量路，结论已写进 `fts-query.ts` 注释。另修正一处自己的实现/注释不一致：注释称保留词内 `-_.` 而实现按标点全切（`gpt-4` 被拆坏），已改回「先按空白切、再剥首尾标点」。

SEC-Batch-7（KDF 档位版本化）动手前后的实测/证伪（21-23）：

21. **我自己在第六节写的 ② 方案范围不足**（动手前 `git grep deriveKeySync` 证伪）：原话是「先在 config.json 落 `kdfParams`，新库用强参、旧库保持原参」——这只覆盖 5 个消费者中的 1 个。全仓唯一派生实现 `deriveKeySync` 同时服务：主密码（库+字段密钥）、none 模式固定混淆密钥（口令/盐是源码常量）、恢复包 `rv1:`、加密导出 `MOXENC1`、备份信封 `PKBK1/PKBK2`；后四者的落盘格式**都没有档位字段**，改默认档位会一次性废掉全部既有凭据混淆、忘密码救援通道与历史备份。故实际收缩为「主密码路径版本化并升 2^17，其余四路显式传 `KDF_LEGACY` 并在文件头写明为什么不能动」，而不是给四类格式各造一个 v2（rv2/MOXENC2/PKBK3 属另一件事，改动面正落在最脆弱的救援/恢复链路上）。
22. **maxmem 恰好等于理论值 128·N·r·p 会直接抛** `memory limit exceeded`（实测：N=2^17 时 maxmem=128MiB 抛错，代码原来写死的 128MiB 上限在旧档 32MiB 下够用、升档后就不够）。所以 `maxMemFor` 取 2×，并由 `tests/kdf-params.test.ts` 一条「故意用理论值调用必须抛、用实现必须不抛」的用例钉住——否则将来谁把 ×2「优化」掉，现行档解锁当场炸。
23. **SQLCipher 上「错密钥」不是在首次 SELECT 才暴露，而是在开库阶段的 pragma 就抛**（实测 `journal_mode = WAL` 处报 `file is not a database`）。两点后果：① 逐档重试必须把整个 open 包进 try（只包 SELECT 会漏），实现已如此；② 抛错时库句柄已经建出来了，调用方一定要 `close()`，否则 Windows 上文件删不掉（我的真库测试就先栽在这里，泄漏的临时目录要手工清理）。
24. **升档的真实收益**：2^15→2^17 只带来 4× 暴破成本（约 +2 bit），而 Batch-6 的 10 位下限带来的是几十 bit——所以档位是「基础设施 + 顺带受益」，不是主要防线。真正的剩余风险仍是 none 模式默认为用户落盘凭据（SEC-1 方案 B，待产品决策）。
25. **「四个消费者钉死历史档」这个结论我自己推翻了**（Batch-7 主体完成后自查 `encryptBackup` 时发现）：备份信封 `PKBK2` 的异机恢复路径不是「保持自己的格式不变」那么简单——`baseKey = masterKeyManager.getDbKey()`（就是当前库密钥）且信封里带的 `masterSalt` 是主密码的 salt，`deriveBackupDbKey`/`decryptBackup` 用「备份密码 + masterSalt」**重现**那把 DB key。因此主密码一旦升到 2^17，按 `KDF_LEGACY` 重现出来的密钥必然是错的，症状是「备份做得出来、换机器恢复时报『备份密码错误』」——数据可恢复性级别的回归，而且 `merge-service.ts:63 cloudKeyFor`（SEC-30 那条链）也复用它。修法（用户选定 D 方案，不引入 PKBK3、不破坏前向兼容）：`openEnvelopeWithPassword` 按 `[记录档→2^15, 2^17]` 逐档派生，**用信封自身的 GCM tag 判定哪一档对**，认证与解密是同一次操作；另加 `verifiedTierBySalt`（只记 masterSalt→档位、**不缓存密钥**，上限 8 条满了清空），使同一备份的后续 blob 不再白跑一次注定失败的旧档。关键安全点由测试钉住：**档位记忆绝不绕过密码校验**（同一 masterSalt 换密码仍报 badPassword）。`tests/backup-kdf-tier.test.ts` 5 例覆盖 2^15 存量备份、2^17 新备份、deriveBackupDbKey 返回源机密钥、密码错、v1 包仍明确拒绝异机。
